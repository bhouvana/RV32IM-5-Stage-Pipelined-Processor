# ADR 0006: RV32M (mul/div), and widening funct7 to its full 7 bits

## Problem

`docs/ROADMAP.md` Phase 5 sequenced RV32M as the natural next step after ISA
completeness (`docs/adr/0005`) -- the next thing that would otherwise get
layered on top of an incomplete decode table. RV32M adds 8 instructions
(`mul mulh mulhsu mulhu div divu rem remu`), all reusing the R-type opcode
(`0110011`) and distinguished by `funct7=0000001`.

## Background: the funct7-width prerequisite

`ALUCtrl.v` only ever received a single bit of funct7 (`Control.v`'s `funt7`
input was wired to `inst_regfd[30]` alone) -- enough to distinguish
`add`(funct7=0000000) from `sub`(funct7=0100000), since those differ only in
bit 5. RV32M's `funct7=0000001` differs from `add`'s `0000000` in bit 0, a
bit that was never threaded through anywhere in this design. There was no
way to add RV32M without first widening that path.

**This was worth doing regardless of RV32M**: any future R-type-opcode
extension (RV32M today; a hypothetical custom op tomorrow) hits the same
wall. Widening once now, structured as an explicit named-constant lookup
(`riscv_defs.vh`'s `FUNCT7_BASE`/`FUNCT7_ALT`/`FUNCT7_MULDIV`) rather than
a wider version of the same magic-number pattern, means the next extension
that needs a new funct7 group doesn't need this same prerequisite step
again.

Changed: `Control.v`'s `funt7`/`funct7` ports (1 bit -> 7 bits, sourced from
`inst_regfd[31:25]`), `reg2.v`'s `funct7`/`funct7_regde` fields (same),
`ALUCtrl.v`'s `funct7_c` port and its entire R-type decode table (rewritten
from a single 6-bit concatenated `case` to explicit `{funct7, funct3}` pairs
-- more entries, but each one unambiguous rather than relying on a hand-
verified concatenation order).

**Regression risk this specifically created**: the I-type `srli`/`srai`
disambiguation in `ALUCtrl.v` did `if (funct7 == 1)` -- correct when
`funct7` was a single bit meaning "inst[30]", silently wrong once `funct7`
became the full 7-bit field (where `sra`'s pattern is `0100000` = decimal
32, not 1). Caught and fixed as part of this same change (`funct7 ==
`FUNCT7_ALT`), not after the fact -- flagged here because it's exactly the
kind of thing a signal-width refactor should be checked against explicitly,
not assumed safe by inspection. Verified: the full existing suite (`sub`,
`sra`, `ctz`, `srai` all directly exercise this path in `arith.s`) passed
with zero regressions after the change.

## Decision: mul/div as single-cycle, not a real multi-cycle divider

`docs/ROADMAP.md` explicitly flagged RV32M as "the project's first real
excuse to design a stall/multi-cycle-execute mechanism generically instead
of ad hoc" -- division in real hardware is not single-cycle-friendly, and a
genuinely authentic implementation would need an iterative divider plus a
new multi-cycle EX-stage stall mechanism (distinct from `Hazard.v`'s
existing single-cycle load-use stall).

**Chosen for this increment: implement `mul`/`div`/`rem` as single-cycle,
using Verilog's native `*`/`/`/`%` operators.** This is:
- Deliberate, not an oversight: a multi-cycle stall mechanism is a
  substantial, independent design effort (needs to correctly interact with
  `Forward.v`/`Hazard.v` while a division is in flight for potentially 30+
  cycles) that deserves its own ADR and its own directed-test-driven
  verification pass, not to be smuggled into an ISA-completeness-shaped
  change.
- Not a functional compromise: the RV32I spec's division-by-zero and
  signed-overflow semantics are implemented exactly (see `ALU.v`), so the
  *results* are bit-for-bit what a correct multi-cycle divider would
  eventually produce. Only the cycle count differs.
- Synthesizable, if not how a real ASIC/FPGA divider would be built: `/`/`%`
  on fixed-width operands synthesize to a wide combinational (or tool-
  inferred multi-cycle) divider in most flows -- functionally correct, but
  DOCS/ROADMAP.md's Phase 7 (FPGA) and Phase 10 (benchmarking, timing) work
  will very likely need to revisit this for real Fmax/area numbers.

Alternatives considered:
- **Build the real iterative multi-cycle divider now.** Rejected for this
  increment on scope grounds, not merit -- it's the right eventual answer,
  tracked explicitly below as future work rather than dropped.
- **Implement mul single-cycle, leave div/rem unimplemented until the
  multi-cycle mechanism exists.** Rejected: mul/div/rem share the same
  opcode/funct7 group and the same ALUCtrl-table shape; splitting them
  across two increments would mean revisiting the same decode table twice
  for no verification benefit (`mul`'s tests wouldn't need to change when
  div/rem's implementation later changes).

`mulh`/`mulhsu`/`mulhu` (the 64-bit-product upper-half variants) needed
their intermediate products computed at explicit 64-bit width *before*
multiplying (via sign/zero-extending both operands to 64 bits first) rather
than relying on Verilog's self-determined width rules for `*` inside a
`>>>` expression -- the latter is exactly the kind of implicit-width
assumption that produced the `sra`/`slt`/`blt` bugs in `docs/adr/0004`, so
this was made explicit from the start rather than fixed after the fact.

## Expected impact

RV32IM: base ISA plus mul/div, matching real RV32IM instruction results
bit-for-bit (including edge cases), at a synthesizable but not yet
cycle-accurate-to-real-hardware cost model for division.

## Validation strategy

`sim/programs/muldiv.s` / `sim/tb/tb_muldiv.v`: all 8 ops, plus the specific
edge cases the spec defines exactly (not "undefined behavior"): division by
zero (`div`/`divu`/`rem`/`remu`, all four), signed overflow
(`INT_MIN / -1`), and a negative-operand `mulh`/`mulhsu`/`mulhu` case
(`A=B=0xFFFFFFFF`) chosen specifically to distinguish the three upper-half
variants from each other (their results differ under that input: `mulh=0`,
`mulhu=0xFFFFFFFE`, `mulhsu=0xFFFFFFFF`) rather than a case where they'd
coincidentally agree. All expected values were computed with a standalone
Python reference calculation, not by hand -- given `docs/adr/0002`,
`0003`, and this session's own `branch_not_taken.s`/`tb_jal.v` mistakes were
all test-authoring errors as often as RTL bugs, hand-arithmetic on 32/64-bit
two's-complement values specifically is not a place to trust manual
verification. Full suite: 13 tests / 67 checks, all passing, zero
regressions in the 12 pre-existing tests (including the funct7-widening
regression risk noted above).

## Future improvements

- The real multi-cycle iterative divider + generic multi-cycle-execute
  stall mechanism, as originally scoped by `docs/ROADMAP.md`. This is now
  the single largest piece of unfinished RV32M work, and should get its own
  ADR when picked up -- it's a genuine microarchitecture change (a new
  stall class), not an ALU tweak.
- `sim/tools/asm.py`'s `R_TYPE` table now needs to stay in sync with
  `riscv_defs.vh`'s `FUNCT7_*`/`ALUCTL_*` defines across two independent
  copies (Python can't `include` the Verilog header) -- same known gap
  noted in `docs/adr/0005`, now with twice as many entries at risk of
  drifting.
